# Hosted room content profile

This is the codec foundation for automatic room keys. Custody, authenticated room
configuration, member release, epoch cutover and client UI activation are separate
unfinished work. The CLI can use the Rust core API; its commands are not wired yet.
Existing local shared-secret rooms remain a distinct profile.

Use a random 32-byte content key directly with IETF ChaCha20-Poly1305, a fresh
random 12-byte nonce per encryption, and an empty AEAD associated-data input.
Authentication covers the context inside the encrypted plaintext. The outer format
is `cow1:` followed by canonical unpadded standard base64 of nonce, ciphertext,
and the 16-byte authentication tag. Reject padding, whitespace and noncanonical
base64 spellings.

The plaintext is a UTF-8 JSON array of exactly five strings:

```
["cowchat-room-message-v1", room_id, key_epoch, message_id, text]
```

`key_epoch` is canonical decimal u64 text (`0` or a nonzero digit followed by
digits, at most 18446744073709551615). Room and message IDs are nonempty strings.
All strings must represent Unicode scalar values; lone UTF-16 surrogates are
invalid. No BOM or UTF-16/32 JSON. Room and message IDs compare by exact UTF-8
bytes, without Unicode normalization. JSON escaping need not be canonical.

The decrypt caller supplies expected room, epoch, and outer message ID. Decryption
returns text only after AEAD authentication, strict tuple decoding and comparison
of all context fields. These checks prevent accepting ciphertext under a different
context; they do not themselves prove membership, sender identity or epoch freshness.
Those checks belong to the room authorizer/writer and authenticated client state.

The profile is chosen from authenticated room configuration. Since the old local
shared-secret profile also uses `cow1:`, never select a profile from that prefix,
try alternate keys/profiles until one decodes, or silently fall back to plaintext.
The typed hosted codec takes raw bytes, never a password or HKDF-derived text key.
Persist ciphertext and message ID before send. A retry reuses both exactly.

## Shared vectors and validation

`fixtures/hosted-room-message.json` is generated by
`node scripts/hosted-room-vectors.mjs`, using Node/OpenSSL as an independent
implementation. The fixture generator intentionally reuses public test keys and
nonces; they must never be used for real messages. The dashboard carries a
byte-identical copy under `frontend/src/lib/cowchat/fixtures/`.

Browser and Rust tests encrypt/decrypt the reference vectors. Swift decrypts the
same vectors and exercises native encrypt/decrypt. All three reject the same
authenticated malformed payloads, wrong scope, wrong key and damaged tags.
The u64 maximum and exact UTF-8 comparisons are covered. The UTF-16 JSON fixture
first reproduced Foundation accepting a payload rejected by the other consumers;
the explicit UTF-8/no-NUL check closes that discrepancy.

These are codec tests, not proof of browser onboarding, real CBSS release, client
command/UI activation, room rotation, or a hosted deployment.
